# Extension Runtime Contract

**Status**: Phase 1 design contract  
**Runtime protocol version**: `2`  
**Capability profile**: `hallpass-v1` (`page.read`, `browser.scroll`, `browser.click`, `browser.enter-text`)

## Purpose and trust boundaries

This contract separates four contexts:

| Context | Trust and responsibility | Explicitly prohibited |
| --- | --- | --- |
| Side panel | Renders account/task state, collects user requests and current-task decisions, exposes Stop; after an explicit unavailable-state recovery gesture may make one response-agnostic `GET /health` solely to trigger Chrome Local Network Access | Credentials, using the bootstrap response as authority, authorization/session/task API or WSS calls, direct tab/content access, policy decisions |
| MV3 service worker | Sole security authority; owns credentials, product channel, tab/origin checks, grants, sequencing, Stop, and dispatch | DOM access, accepting page/model claims as authority, durable Core history |
| Content runtime | On-demand adapter for the current top-level ordinary DOM; returns bounded observations and performs one validated operation | Network, Extension storage, product credentials, page-world bridge, iframe/Shadow DOM traversal, arbitrary code |
| Web page | Untrusted input and effect surface | Calling privileged Extension operations or changing consent/policy |

Only the service worker may use product or page data across a privilege boundary or treat a network
response as authority. The sole side-panel exception is the explicit-gesture, response-agnostic
Local Network Access bootstrap defined below; it grants no product authority. The side panel and
content runtime otherwise communicate through typed Extension messages; they never communicate with
each other or with the page through `window.postMessage`. All task, page, consent, target, and action
state is memory-only except the minimum
session/security state and non-content operation markers explicitly described below.

Traceability: FR-001 through FR-005, FR-007, FR-008; CT-003 through CT-013; SC-001 through SC-011.

## Shared message envelope

Every internal message is a closed JSON-compatible object:

| Field | Rule |
| --- | --- |
| `runtimeProtocolVersion` | MUST equal `2`. |
| `messageId` | Unique opaque ID generated by sender. |
| `runtimeEpochId` | Current service-worker epoch; mismatches are rejected. |
| `type` | Closed message type below. |
| `payload` | Closed type-specific schema; unknown fields fail validation. |

Task-scoped messages additionally require `taskId`. Protected content messages require `operationId`,
the expected tab binding, and the expected top-level `documentEpoch`. Chrome tab IDs and document IDs
remain service-worker-local and are never sent to the product service or rendered as user content.

Payloads are bounded before deserialization or DOM work. Unknown type/version, unexpected sender,
missing task binding, duplicate conflicting ID, terminal task, stale epoch, or invalid schema returns a
stable non-localized error and produces no protected read or effect.

## Side panel to service worker

The side panel opens one long-lived Port named `assistant-control-v1`. A Port is accepted only when
`sender.id` equals `chrome.runtime.id`, `sender.tab` is absent, and `sender.url` is the exact packaged
side-panel URL. The Port receives a sanitized state projection immediately after connection.

| Message type | Required payload | Rule |
| --- | --- | --- |
| `ui.service.retry` | empty | Starts exactly one newer service-health check; it never starts a background poll. |
| `ui.auth.begin` | `locale` | Starts provider-neutral product account authorization after a user gesture. |
| `ui.auth.logout` | empty | Stops active work, invalidates and clears all account-bound trusted local state first, then attempts remote revocation best effort. |
| `ui.task.start` | `clientTaskId`, `userRequest`, `locale` | After reviewed task-submit disclosure, sends `user.request` to the product service; no tab/origin/title/page context is automatically attached. Opening/focusing the panel never implies this message. |
| `ui.safety-disclosure.ack` | `disclosureId`, `presentedLocale` | Confirms the matching locally reviewed origin-classification disclosure is mounted before any remote safety request; it is not page-read consent. |
| `ui.plan.decide` | `planId`, `planVersion`, `planDigest`, `approved`, optional `excludedStepIds` | Applies only to the exact current ordered purpose/context/target/argument/category bindings; denial starts no action. `excludedStepIds` is the set of steps the user removed before approving (002/FR-020): the panel answers about the plan the worker projected, so without it the correction would live only in the panel's own state and the worker would approve a plan the user did not agree to. It is bounded by the plan bound and may not repeat an identifier; the worker refuses the whole approval when one names a step the plan does not have, and approves exactly the kept steps in their reviewed order. An approval that removes every step is recorded as a denial. |
| `ui.capability.decide` | `reviewId`, `requestId`, `grantScope`, `reviewDigest`, `decision` | Creates/denies exactly one projected `general-page-read`, `form-values`, or `action` grant; the panel cannot echo broader fields. |
| `ui.grant.revoke` | `grantId` | Immediately invalidates the matching task grant and prevents new covered operations. |
| `ui.task.stop` | `clientRequestId` | Runs local-first Stop and is idempotent. |

`decision` is `allow-current-task` or `deny`. The worker compares `reviewId`,
`grantScope`, and the echoed local digest with one pending immutable review record; the UI cannot
broaden it. A page-read request containing `page.form-values` creates two independent review
records and decisions. The form-values decision cannot create or broaden the ordinary page-read grant,
and ordinary page-read approval cannot imply form-value approval. `activeTab` is never consent. Exact Plan
approval counts as action consent only when the plan review contains all required locally rendered
purpose/context/target/argument/category/risk/lifetime details; a summary-only plan decision has no authority.
An origin change invalidates grants before a new prompt is shown.

Before emitting `ui.task.start`, the panel uses local selected-locale/English-fallback text to name the
product service, AI-task purpose, and `user.request` data category; the explicit Submit is the task
boundary. If that disclosure cannot render, no task request is sent. Shared runtime schemas accept only
the canonical DataCategory literals from `task-channel.md`; category labels are local dictionary text,
never model/service strings.

Logout first revokes the local task/grants/control lease and removes the session/account binding from
worker state and `chrome.storage.session`. Only after that local transition is confirmed may the worker
use a one-shot in-memory credential copy for `DELETE /v1/auth/session`; remote failure cannot restore
local authorization, and the copy is discarded after the attempt.

## Service worker to side panel

The worker emits complete state projections rather than privileged internals:

| Message type | User-observable projection |
| --- | --- |
| `worker.service.state` | `checking`, `available`, or `unavailable`; unavailable includes only a stable local reason code and the build-pinned local service display address. The reason code is bounded like every other one on this boundary (see below). |
| `worker.auth.state` | `signed-out`, `authorizing`, `signed-in`, `reauthentication-required`, or `policy-blocked`; optional account label and locally mapped stable reason only. Refresh `409` clears local credentials/binding and projects `reauthentication-required` + `auth.account-mismatch`. |
| `worker.context.state` | supported/unsupported, visible origin display, active-control indicator, localized reason code, and two facts about the last page read: which dimension it cut, if any (`visible-text` or `semantic-nodes`), and the strongest class it declined to disclose, if any (`withheld-sensitive` or `withheld-ambiguous`). Both describe the most recent read only: a later read that cut nothing and withheld nothing omits them, and the panel clears the notice rather than leaving a stale one standing. The withholding names a class, never the control it withheld or its value. Both are replayed to a panel that takes the worker over, because a notice only the previous panel saw is a notice the user has lost. It also carries the last resolution (002/FR-026): the `description` that was asked about, its `outcome` (`resolved`, `no-match`, or `too-broad`), and, when the answer was one target, that target's bounded `targetLabel` and closed `targetRole`. A list is never projected here — several candidates are shown as such, and the card of the action that uses the chosen one names the description instead. The notice is cleared, by omission, when the grant it rode on is revoked or the document it named is replaced. |
| `worker.safety-disclosure.review` | opaque disclosure ID plus locally reviewed purpose, recipient class, canonical-origin data category, and Continue control; contains no remote-authored safety copy |
| `worker.task.state` | current lifecycle state, explicit task mode (`undecided`, `answer-only`, `page-read-only`, `single-action`, or `approved-plan`), bounded progressive text, and whether Stop is available |
| `worker.plan.review` | plan ID/version/local digest, exact ordered bindings, locally resolved target labels, normalized text/edit mode, purposes, data categories, the worker-observed origin of the bound document, risk, and current-task/current-document lifetime. Each step also carries `excluded` (002/FR-020), which reports the state of the plan being projected and is therefore only ever true for a plan already decided on: while a proposal is under review the exclusions are the panel's own working state and are not reported back step by step, so a panel that takes the worker over mid-review starts the review again with nothing excluded — fail-safe rather than lossless, because the worker approves nothing without a fresh explicit decision. A step is one of two shapes rather than one shape with optional fields: an action step, which always carries a `risk`, or a wait step (002/FR-027), whose `capability` is `page.wait` and which carries **no** `risk`, no drop target, and no `resolvedFrom` — there is no effect to classify, so the shape refuses a label nothing decided. Both name the element the step acts on or watches, because a step the user is deciding whether to remove is exactly the step they need to see the target of; a wait step's card reads as the condition and the bound in seconds, taken from its own arguments. |
| Review target detail | Every reviewable effect — an `action` consent and each Plan step — carries a required `targetLabel`, `targetRole`, and `risk`. A drag carries a second endpoint as well: `dropTargetLabel` and `dropTargetRole`, present exactly when the reviewed capability is `browser.drag` and refused on anything else, so a card can neither omit where the drop lands nor invent one (002/FR-025). Where the target came from a description rather than a prior read, the review also names that description (`resolvedFrom`, 002/FR-026), so a resolved target is shown before any action uses it. The label is the page's accessible name for one control, bounded to 80 characters; the role is mapped onto the closed set `button`, `textbox`, `combobox`, `control`, `document`, so the page's own role string never reaches the panel; the risk is the local classification (`view-only`, `activation`, `text-entry`, `unclassified`) decided from the capability and that bounded metadata. An effect with no target, and a handle the worker never minted, are named as such rather than described from the request. None of it carries a control value, a selector, or an element reference, it is memory-only, and it is discarded with the page bindings on Stop, terminal, task start, and document change. |
| `worker.consent.review` | opaque review ID and grant scope; pending ordinary page-read, separately pending `page.form-values`, or single action; local review digest, locally resolved target/action/argument summary, purpose, data categories, origin, risk/safety explanation, and current-task/current-document/one-dispatch lifetime as applicable |
| `worker.grants.state` | separate active current-task grants, including the document-bound form-values grant when present, with individual revoke controls |
| `worker.task.terminal` | exactly one outcome plus localized reason/summary. The summary is worker-authored copy and is produced by looking the outcome up in the locale catalogue with the locale the task was started in — never an English literal, so a zh-TW task reports its outcome in zh-TW. A remote summary is never projected verbatim. For a task that ran an approved plan it also carries two worker-authored records. `excludedSteps` (002/FR-021) lists every step the user removed, each with the `position` it was reviewed under — a record of their own decision, not a claimed cause: the worker cannot know which exclusion a later step's failed target check is owed to, so it states what it can attest to and lets the summary say what happened, which is what makes a part-way stop attributable instead of an unexplained failure. It is carried whatever the outcome, and cleared whenever no approved plan governs the task any more — including when a revision is taken out for review, which revokes the approval before the user answers. `run` (002/FR-022) is how far the execution got: `total` kept steps, `observed` steps this worker saw run and verified, the closed `reason` when it knows one, and `stoppedAt` — the reviewed position of the first kept step that did not run, present exactly when the run did not complete, so the panel names the stop in the card's own numbering rather than in kept-step counts. "Completed" is derived from the counts, never asserted. Both are worker-authored: a service-supplied field here could claim a stop the user never asked for. The reason code is bounded like every other one on this boundary (see below). |
| `worker.panel.superseded` | empty; the last thing a replaced Port hears, so it stops reconnecting rather than reclaiming the worker |

Every `reasonCode` a projection carries — on `worker.task.terminal`, on an unavailable
`worker.service.state`, and on `worker.context.state` — is a code and never free text: at most
`REASON_CODE_MAX_CHARS` (80) characters matching `REASON_CODE_PATTERN` (`^[a-z][a-z0-9.-]*$`). The
panel keys reviewed copy off the code and exposes it in the DOM, so a sentence, an HTTP status line,
or a forwarded `Error.message` is refused at the boundary rather than rendered as if it were a code.

Projections never contain access/refresh credentials, PKCE material, WSS tickets, raw page snapshots,
raw target maps, provider payloads, internal Chrome identifiers, or executable selectors. All fixed
labels and stable error codes resolve through reviewed `en-US` and `zh-TW` dictionaries with English
fallback. If safety or consent copy cannot be resolved unambiguously, the worker denies the operation.

Every remote/model-authored display value—including progress, plan summary/step purpose, consent request
purpose, error detail, and terminal summary—is bounded and rendered as inert plain text using normal
text nodes/React escaping. The UI uses no raw HTML, `dangerouslySetInnerHTML`, remote Markdown renderer,
or remote-activated link. A future rich-text/link feature requires a separately reviewed sanitizer and
destination allowlist; it is not inferred by this POC.

Consent UI renders capability and DataCategory names from the local closed enum. Remote `purpose` is
visually identified as task-request detail and cannot replace the fixed local recipient, category,
risk, lifetime, or safety wording. Its exact validated bounded value is nevertheless included in the
local review/Plan digest so the displayed detail cannot change after approval.

A general page-read grant may cover repeated reads during the same task/tab/origin only for its exact
approved purpose digest and non-form category subset. It MUST exclude `page.form-values`. A
separate form-values grant contains exactly that category, depends on a matching active general grant,
and binds the exact current document/SPA epoch. A single-action grant binds exact request ID, purpose digest,
context handle, target handle where applicable, and canonical normalized argument/review digests, and
is consumed by one dispatch. Exact Plan approval creates equivalent grants only for exact steps bound
to purpose plus plan ID/version/digest/step. Any server change to purpose, target, text/edit mode,
capability, category, or argument requires new single-action review or a new Plan version; matching
`stepId` alone is insufficient.

A Plan is reviewable only against a context this worker minted: a proposal whose `expectedContext`
is not a live page binding of this task, or whose steps do not all bind that one context, is refused
and never projected, so a card can never show a service-authored origin. An initial Plan must contain
at least two steps, at least one of which is an effect: since 002/FR-027 the other may be a wait,
which is a control instruction rather than an effect, and a Plan of nothing but waits is refused.
Before its first dispatch, a strictly newer full exact
version may cite the current plan ID/version/digest and requires a new review. After the first dispatch,
the Plan is immutable. Any document change invalidates it; later protected work after a user- or
page-initiated change requires fresh context/safety/consent and a new Plan ID. Completed steps are never
accepted from the server again, replayed, or resumed.

Closing the side panel disconnects the accepted Port. Port disconnect is an implicit
`ui.task.stop` with reason `panel-disconnect`; no active task continues invisibly.

Exactly one Port is accepted at a time. Accepting a new one disconnects the Port it replaces, and a
message from a replaced Port decides nothing: it is dropped with a stable diagnostic code rather
than answered. Because side panels are per-window, the replaced Port belongs to a page that is still
open and would otherwise read the disconnect as a lost worker and reconnect, taking the worker back
from the panel that replaced it. So the worker sends that Port one final `worker.panel.superseded`
before closing it; a panel that receives it stops reconnecting and says so, instead of trading the
worker back and forth.

A newly accepted Port is handed the live task before anything else, in this order:
`worker.task.state`, `worker.context.state`, the review still awaiting an answer
(`worker.safety-disclosure.review`, `worker.consent.review`, `worker.plan.review`), then
`worker.grants.state`. The records are re-sent, never re-minted: the review keeps its original ID and
local digest, so the decision the panel sends back still matches the one the worker is holding. A
Port that connects while no task is running receives none of these. This re-projection restores what
the panel may answer; it never resumes a task, replays a step, or revives a terminal one.

The panel mirrors that boundary. When its Port disconnects, or when a projection arrives under a
different `runtimeEpochId`, it drops every review card, the Stop control, the progress text, and the
control indicator before applying anything new: a card whose worker is gone is a decision nobody
would receive. It reconnects silently a bounded number of times (a build constant, currently six);
past that it stops retrying and tells the user to reopen the assistant, which is not presented as an
authorization state. Whether the assistant is controlling the tab and whether Stop is available are
worker projections, never inferences from the panel's own clicks.

On Port acceptance, the worker starts one five-second-bounded `GET /health` probe and projects
`checking`. Only HTTP 204 projects `available` and permits session restore, sign-in, or protected
work. Non-204, rejection, and timeout project `unavailable`. To satisfy Chrome 142+ Local Network
Access without weakening worker authority, the unavailable panel's explicit recovery gesture may make
one five-second-bounded `GET /health` with local target-address intent solely to present the browser
permission decision. The panel discards status, body, and errors, prevents duplicate requests while
pending, then emits exactly one `ui.service.retry`. It performs no other product-service request.
Each `ui.service.retry` starts one newer worker probe, with no continuous polling; a
monotonic generation guard prevents an older probe or restore result from replacing the newer state.

## Origin-safety disclosure sequence

The service worker always computes the local allow/deny/unknown decision first. Local deny blocks with
no remote call; local allow proceeds to the separate capability-consent gate. For local unknown:

1. the worker resolves locally reviewed selected-locale text, falling back to reviewed `en-US`;
2. if purpose/recipient/data-category wording is missing or ambiguous, it records disclosure failure and
   sends no classifier request;
3. otherwise it projects `worker.safety-disclosure.review` and waits for the exact matching
   `ui.safety-disclosure.ack` from the accepted side-panel Port;
4. only after that acknowledgment does it call the unauthenticated origin-assessment endpoint with a
   body containing exactly the canonical origin; and
5. only a current valid `allow` may proceed to a separate page/action consent decision.

The disclosure ID, task/account data, full URL, and acknowledgment never enter the classifier request.
Closing the panel or pressing Stop while disclosure is pending cancels it and sends nothing.

### Disclosure lifetime

One acknowledgment covers that exact canonical origin for the current task. It is task-scoped: a new
task discloses again, and so does a different canonical origin within the same task.

The classifier's own decision lifetime is shorter than a task can be. When it lapses while the task is
still running on the same acknowledged origin, the worker re-assesses that origin under the existing
acknowledgment and MUST NOT present a second identical disclosure. Repeating it strands the task behind
a review the user has already answered, while telling them nothing they were not already told: the
purpose, recipient, and data category are unchanged, and the request still carries exactly the canonical
origin. Re-assessment stays fail-closed — deny, unknown, invalid or lapsed validity, an unavailable
service, and any tab or document drift each block the protected work and end the request rather than
allowing it.

This lifetime is the only thing the lapse changes. It grants no reuse of a stale `allow`: every
continuation requires a current valid decision, and the separate page/action consent gate is unaffected.

## Service worker to content runtime

The worker uses no static content script. After a user-triggered task needs approved page access, it:

1. resolves the current active tab and rejects non-HTTP(S), non-top-level, browser-internal, extension,
   store, PDF-viewer, privileged, inaccessible, or otherwise unsupported contexts (a wait is the one
   exception; see below);
2. verifies origin safety and current-task consent;
3. injects the packaged content-runtime bundle with `chrome.scripting.executeScript` into frame `0` in
   the `ISOLATED` world only; and
4. binds the injected runtime to the current task, runtime epoch, tab, top-level document, and a fresh
   unguessable channel nonce held by the worker.

Injection is idempotent only within that exact document binding. No remote code, `eval`, dynamic module
URL, `MAIN` world execution, page-world bridge, iframe injection, or broad background observation is
allowed.

A wait (002/FR-027) is the one round trip that does not resolve the active tab. Its poll goes to the
**leased** tab by id (`evaluateConditionOnLeasedTab`) — the same rule a cancel follows, and for the
same reason: the document being watched lives there even after the user has switched tabs. A wait
spans seconds and touches nothing, so it has no business ending because of where the user is looking.
A leased tab that is gone, or that no longer shows the task origin, has no document left to watch and
is `stale-context`. The rule for the action step the wait was waiting for is unchanged: an effect is
still refused at dispatch unless the leased tab is the active one, because that rule belongs to the
effect rather than to watching for it. A recorded follow-up, not blocking: the evaluator reaches the
page through the same runtime-ensure every other operation uses, so a poll against a leased tab whose
background document was replaced may inject the runtime bundle into that new document only to discover
the epoch mismatch and answer `stale-context`; a probe-without-inject primitive would be tighter.

The worker sends these closed operations one at a time:

| Message type | Required payload | Result |
| --- | --- | --- |
| `content.probe` | expected document binding and the worker-minted 128-bit binding nonce | Supported top-level context metadata only; no page text |
| `content.collect-page` | general page-read grant ID, optional distinct form-values grant ID, requested data categories, exact document binding, injected bounds | Bounded/redacted ordinary-DOM snapshot, optional category-gated form-value items/withholding metadata, truncation/inaccessibility disclosures, opaque target handles |
| `content.execute-action` | single-action or approved-plan-step binding, and the action with its arguments as one closed pair built from the same module the task channel validates against, so an argument the service could not send cannot reach the page by another route | One observable success/non-success result plus post-effect context evidence |
| `content.resolve-target` | general page-read grant ID, the bounded `description`, the worker-supplied `maxCandidates`, exact document binding | Handles only: `{ ok: true, outcome: "resolved", candidates: [ { targetHandle } ] }` within the bound, `{ outcome: "no-match" }`, or `{ outcome: "too-broad" }` |
| `content.evaluate-condition` | general page-read grant ID, `targetHandle`, `condition`, exact document binding | One boolean: `{ ok: true, holds }` |
| `content.cancel` | operation ID | Cancels queued/not-started work; never asserts rollback of a begun effect |

`content.resolve-target` (002/FR-026) rides on the general page-read grant its payload cites; the
runtime matches the description against each minted handle's label, a button's visible text, and the
control's role, over elements the document still shows. Its reply carries **handles and nothing else**:
`role`, `label`, and `kind` never travel back from the page, because the worker re-projects every
candidate from the target metadata it minted at collection, and a role or a label the page authored
could only describe an element the review never showed. A handle the page names that the worker never
minted fails the whole resolution rather than being passed off as "nothing matched".

`content.evaluate-condition` (002/FR-027) rides on the same grant and asks one question about one
handle the worker already holds, answered with one boolean. The wait's bound is deliberately absent
from the payload: the timer is the worker's and the page is asked once per poll, so a page is never
told how long the product is prepared to wait. Everything else a wait can end with — the bound, a
Stop, a document change — is the worker's own decision, made from state the page cannot see. A wait is
not a read, so no text, handle, or descriptor travels back with the answer.

Content results use the same closed status literals as the task channel: `succeeded`, `denied`,
`unsupported`, `inaccessible`, `stale-context`, `cancelled`, `attention-required`, and `failed`. A
refusal from the runtime instead names one reason from its own closed set
(`CONTENT_EXECUTION_REFUSAL_REASONS`), so a reason the worker does not know cannot reach the task
channel as an error code: `denied`, `submission-guard`, and `unsupported-key` are decided from policy
at effect time against the live element; `stale-target`, `missing-target`, and `missing-sink` mean the
action could not be carried out; `invalid-message`, `stale-binding`, `stale-context`, `cancelled`, and
`unsupported-page` mean the frame, or the binding it cited, was not acceptable to the runtime. Whether
a refusal is a denial (a policy decision that will not change on retry) or a failure (the step could
not be carried out) is the worker's decision and is deliberately not encoded in the reason.

The content runtime accepts messages only from `sender.id === chrome.runtime.id` with the injected nonce
and matching runtime/task/document binding. The nonce is minted by the worker, established by
`content.probe`, and repeated on every later frame of that binding; a frame whose nonce is not the one
this binding was established with is refused as `stale-binding`, so a frame captured under an earlier
binding cannot be replayed into a live one even when its task and epoch still match. A probe from the
same task and worker epoch re-establishes the nonce without invalidating the handles that task holds;
a probe from a different one is a new conversation and drops them. `content.cancel` never probes: it
carries the nonce the worker already holds, because probing would rebind a runtime that may already
belong to a successor task. Its replies are accepted only when `sender.id` matches,
`sender.tab.id` is the worker-held expected tab, `sender.frameId === 0`, and `sender.documentId` matches
the expected top-level document. Missing or ambiguous sender evidence fails closed.

## Page collection contract

`content.collect-page` walks only the current top-level document's ordinary DOM. It returns a bounded,
task-relevant representation of visible/meaningful structure and text, not serialized HTML. Before
returning it:

- without an active matching form-values grant, every current form value and selected-option state is
  excluded;
- with the distinct current-task/current-document `page.form-values` grant, a closed local policy
  may include only bounded task-relevant ordinary input/textarea values and select selected-option
  display state conclusively classified non-sensitive;
- password, hidden/file, one-time-code, payment-card, sensitive-autocomplete, product-credential, and
  ambiguous fields expose no value, length, hash, or partial content; optional withholding records
  contain non-value role/label/type and `withheld-sensitive` or `withheld-ambiguous` only;
  checkbox/radio checked state remains excluded from `hallpass-v1`;
- page title and current top-level text selection are bounded/redacted and returned only when their
  exact `page.title` or `page.selection` category is granted;
- hidden/inaccessible material and unrelated attributes are omitted;
- each interactable target receives an opaque, document-epoch-bound handle kept only in content memory;
- truncation states which dimension reached its injected bound; and
- an answer dependent only on iframe, Shadow DOM, canvas, WebGL, or another unsupported surface is
  reported `unsupported` or `inaccessible`, never inferred or called partial success.

Every reload, SPA/document or origin change, reinjection, Stop, grant revocation, task terminal state,
or runtime epoch invalidates every form-value snapshot/grant. Every new document, origin change,
reinjection, Stop, task terminal state, or runtime epoch also invalidates the target map and all
outstanding handles.

Immediately before calling `content.collect-page`, and again before forwarding its returned payload,
the worker rechecks nonterminal task/channel state, Stop/control lease, the general page-read grant and
the distinct form-values grant when that category is present, selected tab, and current
document/origin after the last awaited prerequisite. Any intervening close/Stop/revoke/context change
starts or transmits no protected page collection; the returned payload is dropped before WSS forwarding.

## Action contract

The exact action enum uses the same canonical literals as the domain and task channel:
`browser.scroll`, `browser.click`, `browser.enter-text`, `browser.key-press`, `browser.hover`,
`browser.double-click`, and `browser.drag` (`BRIDGE_ACTIONS`; the last four added by 002/FR-024 and
FR-025 under FR-028's amendment of 001/FR-005). `page.read`, `page.resolve`, and `page.wait` are
capabilities of the same profile but are not actions, and are not expressible through
`content.execute-action`. Risk and sensitivity remain local policy checks rather than alternate wire
names. Any assistant-initiated navigation literal, and secondary (context-menu) activation, are
outside `hallpass-v1` and are rejected before grant, operation-marker creation, or content dispatch.

Before dispatch, the service worker revalidates task, account, execution mode, grant, origin, current
selected tab, top-level document, target handle, action risk, and sequential-operation ownership. A
multi-step action must match the next approved plan step; a `single-action` task has exactly one browser
effect slot and rejects any later action. The content runtime then rechecks document epoch and target
presence immediately before the effect.

Execution mode is checked first, from worker-held state alone, so a request the task can never run
costs the user no disclosure or review card and the service no origin assessment. `executionBinding.mode`
is a service claim, not an instruction:

- `single-action`: the slot is consumed the moment the user allows the action — before the active-tab
  re-check and before any dispatch, so a request arriving while that decision is being applied cannot
  open a second card — and every later action request returns `denied` /
  `capability.single-action-exhausted`. A task that has spent
  its slot also refuses a Plan proposal and every plan-step request, because none of its steps could
  run. Conversely, once a Plan has been proposed, a `single-action` request is not the next approved
  step and returns `denied` / `plan.step-mismatch`.
- `approved-plan-step`: the request must cite the approved Plan's exact ID and version, name the next
  step that has not yet dispatched, and reproduce that step's review digest — capability, purpose,
  expected context, data categories, and canonical arguments. A match is the action consent for that
  step: exact Plan approval already created the equivalent grant, so the step dispatches without a
  second card and under the same worker-owned fence. Anything else returns `denied` /
  `plan.step-mismatch`, and a step requested after the Plan expired returns `denied` / `plan.expired`.
  A completed step is never accepted again.
- Any other mode on a browser effect is `failed` / `invalid-binding`.

Every refusal answers the request and starts no effect, no marker, and no consent card. The mode is
asked again when the user answers an action card, not carried from the moment it was projected: a Plan
accepted for review meanwhile has already changed what the task may run.

Effect dispatch uses one worker-owned fence. After awaiting `dispatched` marker confirmation and any
probe, the worker repeats the nonterminal/Stop/grant/context/target checks immediately before initiating
the content call. If Stop, revoke, tab/document/origin change, or terminal state occurred meanwhile, no
content call is made; the task projects cancellation/denial and safely cleans the marker after projection.

The fence also holds across the executor's own probe. The worker hands the executor the fence as a
callback together with the leased tab ID; the executor refuses any other active tab before it probes or
injects, and after its probe, immediately before it sends `content.execute-action`, it asks the fence
again. Only a true answer commits the effect: from that moment a Stop must treat the effect as possibly
run. A false answer means the executor sends nothing and reports `fence-refused`; the worker removes
the marker and projects cancellation when Stop caused it, denial when a revocation did, and
`stale-context` when the reviewed binding is no longer the live one. An executor failure before that
commit (no active tab, unsupported page, probe or injection failure) is likewise a known failure with
its marker removed, never an uncertain effect. An action approval is bound to the tab it was reviewed
on: a decision that arrives after the user switched tabs is refused before any executor runs, so no
other tab is probed or injected.

- `browser.scroll` changes the top-level document viewport or brings a valid current target into view.
- `browser.click` activates one ordinary target only after the worker has classified the requested
  effect as low risk. Payment/purchase confirmation, destructive deletion, account/security change,
  public/final submission, file upload, and ambiguous effects are forbidden.
  Anchors, link-like targets, form-associated submit/reset controls, file controls, controls with any
  URL/form action, and script-driven activation that may navigate or cannot be classified as low-risk
  and non-navigation are denied before the effect. Post-effect origin checking is detection, never
  retroactive authorization.
- `browser.enter-text` enters the exact bounded approved text only into a current editable target
  not identified as password, OTP, payment-card, file, or otherwise sensitive. It does not submit.
- `browser.key-press` delivers one key from the closed allow-list — `Enter`, `Tab`, `Escape`, the four
  arrows, `Home`, `End`, `Backspace`, `Delete` — with `Shift` as the only modifier and only with
  `Tab`. A key outside the list is refused before any event. A submission guard refuses the
  confirmation key wherever its default effect on the focused element would submit a form or navigate:
  a single-field form, where implicit submission still fires, and a form with a submit control
  associated with it, including one outside the form. The same read policy that decides text entry
  decides the target: a control the policy withholds is refused even with a handle in hand. Delivery
  is verified by the focused element keeping its identity — a key whose handler moved focus was
  delivered, but its outcome is no longer attributable to the control the user was shown.
- `browser.hover`, `browser.double-click`, and `browser.drag` deliver only the synthetic events a
  page's own handlers listen for: pointer and mouse `over`/`enter`/`move` for a hover, two activations
  and a `dblclick` for a double activation, and the HTML drag-and-drop sequence (`dragstart`,
  `dragenter`, `dragover`, `drop`, `dragend`) with one shared `DataTransfer` for a drag. Synthetic
  events do not make CSS `:hover` match, so a menu opened purely by a stylesheet stays closed while a
  script-driven one opens; and a drop is delivered only where the page cancelled `dragover`, the
  browser's own rule for accepting a drag, so a drag the page did not accept reports nothing moved.
  The click classification decides all three, and both endpoints of a drag — the stricter deciding —
  before any event. A drag's two endpoints must be distinct. Reach is bounded by collection: the
  collector mints handles only for `<button type="button">` and ordinary text controls, so a gesture
  can target nothing a click could not.

Effect-time classification re-reads the live element immediately before the effect and applies the
same closed local form-value policy that decides `page.form-values` disclosure: text may enter only a
rendered, enabled, writable `input` or `textarea` that the policy conclusively classifies as ordinary
(allow-listed name, ordinary type, no sensitive `type`/`autocomplete`/name part). An unnamed,
unlisted, sensitive, ambiguous, hidden (`hidden`, `aria-hidden="true"`, or not rendered), read-only,
disabled, or non-text control fails closed, and so does a `contenteditable` region, which carries no
name the policy could classify. A click is refused for anchors, link-like roles, `submit`/`reset`/
`image`/`file` inputs, buttons without an explicit `type="button"`, any `formaction`, `form`,
`formtarget`/`target`, or `download` attribute, `a`/`area`/`form`/`select`/`option`/`label`/`iframe`/
`object`/`embed` elements, and hidden or disabled controls (including a control disabled through an
ancestor `fieldset`). A handle minted at collection time confers no eligibility: an element mutated
into any of these states after collection is refused at the effect.

Only a post-operation observable check can return `succeeded`. A missing/stale required target,
unexpected or unconfirmed navigation/document change, selected-tab or focus loss, unsupported context,
denial, or ambiguous effect returns the matching non-success status and starts no later step. Document
replacement is never a successful POC action. Actions are strictly sequential and never span tabs.

The post-operation check has three layers. The content runtime compares the document URL before and
after a click or text entry and reports `documentChanged`; a same-document change (history API, hash)
is observable there. The worker then waits a bounded settle window (a build constant recorded as a
verification bound under A-010, not a product latency number) during which a `tabs.onUpdated` loading
signal for the leased tab marks the in-flight effect. Finally the worker
re-probes the runtime already bound to that tab without injecting; no answer, a different document
epoch, or a different origin means the effect replaced or navigated the document. Any of the three
yields `attention-required` with `errorCode: "document-changed"`, marks the operation marker
`uncertain`, invalidates the document binding, and transmits an empty result. Scrolling cannot replace
the document and is verified by the runtime reply alone.

Each added action carries its own evidence through the same three layers (002/FR-024, FR-025). A key
press is verified by the focused element keeping its identity, a hover by the target still being
connected and rendered, a double activation by its activation count, and a drag by the dragged
element having moved relative to the drop target — a scroll that carried both endpoints is not a
move. Evidence that cannot be established is uncertain, never success, and it names its own cause
from the closed `ATTENTION_REQUIRED_CAUSES` set rather than borrowing `document-changed`:
`focus-lost`, `target-not-visible`, and `not-moved` leave the document, its handles, and the Plan
standing and put only the attribution of that one effect in doubt, so the run ends
`effect-unverified`, while `document-changed` — including a document replaced mid-gesture, which ends
a drag before its drop — drops the bindings and expires the Plan as it always has. A refusal the
content runtime decides from policy at effect time (the submission guard, a key outside the set, a
target the read policy withholds) is a `denied` result naming that guard: it started no effect, is
not uncertain, and is neither `failed`, which would invite a retry, nor `unsupported`, which would
say the capability is absent from the profile.

A wait (002/FR-027) samples its condition on the same kind of build constant: the poll interval is
recorded under A-010 exactly as the settle window is, and is a sampling rate rather than a product
bound — the bound is the protocol's `maxWaitMs` (15 000 ms), which the request carries. One poll is
a page round trip and so carries the same ten-second content-operation deadline every other round
trip does; that deadline can therefore outlast a short wait, which is why the bound runs on a
worker-owned timer rather than only between polls. A poll that never comes back ends the wait at its
bound (`failed` / `bound-reached`), and its late reply is ignored.

The remote `server.terminal` is untrusted input. The worker records every capability result it
transmits. Once any effect was transmitted as uncertain — `attention-required` with any cause from
the closed `ATTENTION_REQUIRED_CAUSES` set (`document-changed`, `focus-lost`, `target-not-visible`,
`not-moved`, `execute-uncertain`, `grant-revoked`), of which only `document-changed` drops the page
bindings and expires the Plan — every later
remote terminal projects `attention-required`, with the local reason `task.effect-uncertain` unless the
service itself reported attention-required: a service cannot relabel an unverified effect as success,
failure, denial, or a clean cancellation. A runtime refusal that started no effect is a plain
`denied`/`failed` result and never counts as uncertain. Otherwise a remote `success`
is projected only when the task received no capability or Plan frame at all (`answer-only`) or every
transmitted result was `succeeded` and, for an approved Plan, every one of its steps was observed;
a service that stops asking part-way through an approved Plan and then reports success is claiming work
this worker never saw run, so that terminal projects `failure` (`task.unverified-success`); a remote `success` after a denied, unsupported, stale, or failed
required operation projects `failure` (`task.unverified-success`). Downgraded terminals use reviewed
local summary copy instead of the remote summary.

## Lifecycle, replay, and Stop

On every service-worker initialization, the worker creates a new unpredictable `runtimeEpochId` and
reads only minimum authorization/security state and operation markers from `chrome.storage.session`.
The storage access level remains trusted Extension contexts; content scripts receive no storage access.

An operation marker contains only runtime epoch, opaque task/request/account IDs, expiry, and
`prepared`/`dispatched`/`observed`/`uncertain` state—never action category, prompt, URL/origin, page
content, target text, arguments, or result content. The worker first writes `prepared`; immediately before it calls
`content.execute-action`, it MUST persist `dispatched` and await successful storage confirmation.
`dispatched` is deliberately a write-ahead risk boundary meaning that the effect may occur, not proof
that it did occur. If the write fails, the content call is not made. A marker from an earlier epoch is
never replayed. Recovery is fixed: `prepared` projects cancellation/`lifecycle-interruption`;
`dispatched` or `uncertain` projects attention-required; and `observed` without its memory-only exact
result projects failure/`lifecycle-interruption`, never success. Each blocks later effects. The marker is
kept until that terminal/interruption projection reaches an accepted side-panel Port or finite expiry,
then removed. Marker mutations are applied strictly one after another: a late `observed` write can
never revive a marker the terminal already cleared, and overlapping writes never drop each other's
markers. Logout/account mismatch clears account-bound state after projecting the safe local state;
browser restart or extension reload/update restores no task.

Stop order is fixed:

1. atomically mark the task stopping, revoke the control lease and all grants, and discard every
   form-value snapshot;
2. reject queued/new capability and UI decisions;
3. send `content.cancel` to the leased tab for work not yet begun, naming any in-flight operation by
   its own operation ID, and invalidate target handles;
4. mark any begun but unconfirmed effect `uncertain`;
5. project stopped/cancelling state to the side panel; and
6. attempt WSS/HTTPS remote cancellation without waiting to enforce local Stop.

An approved Plan expires with the document its steps were bound to: both a bound-document change and an
effect whose own verification failed end it, so every later step request is refused rather than
dispatched against a document nobody reviewed. A document change while a Plan is still awaiting the
user's decision ends the task as a cancellation (`plan.document-changed`), and revoking the general
page-read grant the Plan was built against ends it the same way (`plan.grant-revoked`); either ends as
`attention-required` instead when an earlier effect of the same task was already transmitted as
uncertain. Neither is reported to the service as a plan decision: the user did not answer the Plan.

Exactly one terminal state is projected. If certainty about an in-flight effect is unavailable, the
outcome is `attention-required`, never success or a claim of rollback. An effect whose result was
already observed against the same document leaves nothing unconfirmed, so a Stop that arrives after it
(for example while the next plan step awaits consent) is a cancellation, unless an earlier effect of
the same task was transmitted as uncertain, in which case the Stop still needs attention.

## Task bootstrap

`POST /v1/tasks` answers with the task, the single-use connection ticket and a `channelUrl`. The
worker treats that answer as a destination, not as authority: before any socket exists it compares
`new URL(channelUrl).origin` with the WSS origin this build was pinned to, and refuses the task with
`task.invalid-bootstrap` if they differ. A service that has been redirected, or answered by
something else, therefore cannot choose where the channel - and the credential that opens it - is
sent. The same check rejects a `ws://` URL, since the pinned origin is always `wss://`.

The pinned origin is a build-time value: it comes from the extension's build configuration, which is
also what the manifest's CSP `connect-src` names, so an artefact can only ever reach the endpoints it
was built against.

## Channel liveness

An accepted channel is kept alive from both ends, so neither waits forever on a peer that is gone.
The worker sends `client.heartbeat` every heartbeat interval carrying the highest server sequence it
has observed, and treats silence longer than the lease deadline as a lost lease: it interrupts the
task locally (`lease-expired`), which halts it through the same path as any other lifecycle
interruption and projects cancellation, or attention-required when an effect may already have run.
The service arms the same deadline on its side, renews it on every valid client frame, and on expiry
projects one `cancellation` terminal with `lifecycle-interruption`, aborts the provider, and drops
the transient task record. Both durations are deployment inputs recorded under A-010, not product
latency numbers; the heartbeat also gives Chrome the WebSocket traffic that keeps the MV3 service
worker from idling out under a task that is genuinely running.

## Navigation observation

The POC requests neither `tabs` nor `webNavigation` permission. While a panel/task binding exists, the
worker filters the public `tabs.onUpdated` signal to the leased tab ID and treats a matching event only
as a dirty hint; it does not assume `changeInfo.url` or `tab.url` is available outside the active grant.
Before the next protected step, a fresh active-tab/content probe determines the actual state.

If the tab is no longer selected/bound, protected work pauses and never migrates. If the canonical
origin changed, the worker invalidates the document/snapshot/target binding and current-task grants,
reassesses safety, and obtains fresh consent. A same-origin reload or SPA/DOM change invalidates the
document/snapshot/target binding and every exact action/Plan-step grant, requiring re-probing and renewed
exact action review; it does not by itself revoke an otherwise valid same-origin page-read
task/category grant, but it always revokes the distinct `page.form-values` grant and discards its
snapshot. Same-origin changes that produce no reliable tab event
are still detected by the mandatory pre-step probe; no background page surveillance is introduced.

An unexpected document replacement during an attempted action invalidates the complete action/Plan
binding and yields non-success or attention-required according to effect certainty. A user- or
page-initiated replacement is a compatibility event, not assistant navigation authority: later
protected work requires the applicable fresh invocation, reinjection/probe, safety evaluation, consent,
and a new exact Plan ID. No old context, grant, step, or result resumes.

R-013's DNR/alarm containment design remains a post-POC Navigation Lab only. Runtime protocol `2` and
`hallpass-v1` contain no navigation dispatcher, guard, rule/alarm state, destination category, or success
result. Adding a future navigation profile requires explicit product approval plus reviewed action,
data, permission, lifecycle, and two-release-Chrome evidence; an implementation cannot infer it from
this observation logic.
